# 上架前後端：CORS

> 小白的想法： 「前端放在 localhost:3000，後端在 localhost:8080。瀏覽器一直報錯說擋住了請求，所以我去 Google 抄了一段設定 Access-Control-Allow-Origin: *，終於通了！」
> 
- **資安風險：**
    - 代表允許「任何」網站的前端程式碼呼叫你的後端 API。
    - 雖然 CORS 本質是瀏覽器的保護機制，但過度寬鬆的設定配合其他漏洞（如內網應用），可能導致惡意網站讀取使用者的敏感資料。
    - 若設定 `Access-Control-Allow-Credentials: true` (允許帶 Cookie)，則絕對不能設為 。
- **防禦策略：**
    - **白名單機制：** 只允許特定的 Domain（如 `https://www.my-frontend.com`）存取後端。
    - 區分開發環境與生產環境的 CORS 設定。

# 傳輸層安全：HTTPS v.s. HTTP

> **小白的想法：**「我在本機開發用 http://localhost 跑都很正常啊！聽說申請 SSL 憑證要錢，而且伺服器設定好麻煩。反正我又不是做銀行網站，應該不會有人無聊到來竊聽我的小網站吧？」
> 
- **資安風險：**
    - **明文傳輸 (Plain Text Transmission)：** HTTP 協定是明文傳輸的。這意味著當使用者在星巴克或機場使用公共 Wi-Fi 登入您的網站時，駭客只需使用簡單的封包監聽工具（如 Wireshark），就能直接看到封包裡原本的帳號與密碼。
    - **中間人攻擊 (MitM)：** 除了竊聽，攻擊者還可以攔截並篡改傳輸中的資料（例如在網頁中插入惡意廣告或挖礦程式），而使用者和伺服器端完全無法察覺資料已被動手腳。
    - **瀏覽器信任警告：** 現代瀏覽器（Chrome, Edge）會對非 HTTPS 的網站標示「不安全」，這會極大降低使用者對網站的信任度，甚至導致登入功能被瀏覽器阻擋。
- **防禦策略：**
    - **強制開啟 HTTPS：** 使用 SSL/TLS 憑證加密傳輸通道。現在已有 **Let's Encrypt** 提供免費且自動化的憑證服務，成本已不再是藉口。
    - **設定 HSTS (HTTP Strict Transport Security)：** 在伺服器回應 Header 中加入 HSTS 設定，強制瀏覽器在未來的一段時間內，只允許透過 HTTPS 連線，防止駭客透過「降級攻擊」將使用者導回不安全的 HTTP。
    - **Cookie 設定 Secure 屬性：** 確保登入後的 Session Cookie 帶有 `Secure` 標籤，限制該 Cookie 只能在 HTTPS 連線下傳輸，防止在不小心切換到 HTTP 時洩漏。
