# 登入後：XSS(cross-site scripting)攻擊

通常現代框架（React, Vue, Angular）預設會進行編碼，如果這個小白至少會使用框架的話。

但是將資訊存在web storage（session storage）或local storage就是有被xss的風險。

什麼時候會需要用到web storage（session storage）或local storage?

- 跨session
    - 偏好設定/客製化
    - 表單數據保存
- 跨tab的資料
    - 購物車/訂單狀態
    - 臨時 UI 狀態
    - 多步驟流程


---
## 防禦策略

## 1. 替代方案實作：使用 `HttpOnly` Cookie

這是取代在 Web Storage 中儲存認證令牌（如 Session Token 或 JWT）的最重要步驟。這需要在**後端伺服器**層面實作。

---
### 步驟 A: 後端設定 `HttpOnly` Cookie

當使用者成功登入後，後端伺服器在 HTTP 響應中，不將 Token 放入 JSON 主體回傳，而是通過 `Set-Cookie` 響應標頭設定 Cookie。

---

**實作範例（Node.js Express / Python Django/Flask）：**

伺服器在響應中加入以下標頭：

HTTP

`Set-Cookie: auth_token=jwt_string_here; HttpOnly; Secure; SameSite=Strict; Path=/; Expires=...`

| **屬性** | **實作作用** | **實作位置** |
| --- | --- | --- |
| **`HttpOnly`** | **核心防禦：** 禁止所有客戶端 JavaScript 存取此 Cookie。 | 伺服器發送 `Set-Cookie` 標頭時設定。 |
| **`Secure`** | 確保 Cookie **只能通過 HTTPS** 連線傳輸。 | 伺服器發送 `Set-Cookie` 標頭時設定。 |
| **`SameSite=Strict`** | 大幅防禦 CSRF (跨站請求偽造) 攻擊。 | 伺服器發送 `Set-Cookie` 標頭時設定。 |

---
### 步驟 B: 客戶端 (Client-side) 如何驗證

客戶端不需要使用 JavaScript 存取 Token，瀏覽器會**自動**將這個 `auth_token` 帶入**每一個**發往伺服器 API 的請求中。

- **發送請求：** 客戶端發送 API 請求時，例如使用 `fetch` 或 Axios：JavaScript
    
    `// 瀏覽器會自動附加 HttpOnly Cookie，客戶端程式碼無需處理。
    fetch('/api/user/profile', {
      method: 'GET',
      credentials: 'include' // 確保請求攜帶 Cookie
    })`
    
- **後端驗證：** 後端收到請求時，直接從請求標頭中讀取 `auth_token`，進行驗證和授權。

---

## 2. 實施安全標頭與部署防禦

這些是需要由**伺服器配置**或**基礎設施**提供的額外防禦層。

---
### 步驟 A: 設定 Content-Security-Policy (CSP)

這需要伺服器在 HTTP 響應中新增 `Content-Security-Policy` 標頭。這是**抵禦 XSS 的第二道防線**。


---

**實作範例：**

HTTP

`Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedcdn.com; object-src 'none'; base-uri 'self';`

| **指令**                      | **實作作用**                                                   | **實作位置**                         |
| --------------------------- | ---------------------------------------------------------- | -------------------------------- |
| **`default-src 'self'`**    | 限制所有資源（如圖片、字體、Ajax 連線）只能從應用程式本身的網域載入。                      | 伺服器配置文件（如 Nginx, Apache, 或應用框架）。 |
| **`script-src 'self' ...`** | 只允許從應用程式本身和指定的受信任 CDN 載入 JavaScript 腳本。                    | 伺服器配置文件。                         |
| **`object-src 'none'`**     | 完全禁止 `<object>`, `<embed>` 和 `<applet>` 標籤，防止 Flash 等插件攻擊。 | 伺服器配置文件。                         |

---
### 步驟 B: 後端過濾使用者輸入 (Input Validation)

在將使用者輸入的資料存入資料庫或用於其他操作之前，後端必須進行驗證、清理和消毒。

---
**實作細節：**

- **白名單驗證 (Whitelisting):** 只允許預期的輸入格式。例如，電話號碼只允許數字和特定符號；使用者名稱只允許字母數字。
- **輸出編碼 (Output Encoding):** **在呈現資料給使用者之前**，對所有動態內容進行編碼（如前所述）。
- **使用框架提供的過濾：** 現代框架通常有內建的函式來安全地處理使用者輸入。例如，在 PHP 中使用 `htmlspecialchars()`。


---
### 步驟 C: 應用部署與驗證

- **子域名分隔 (Subdomain Separation):** 如果您有多個應用程式（例如 `app.example.com` 和 `blog.example.com`），請確保它們在不同的域名/子域名下，防止一個應用程式的 XSS 漏洞影響到另一個應用程式的 Web Storage 或 Cookie。
- **停用 X-XSS-Protection：** 舊的瀏覽器標頭 `X-XSS-Protection` 在現代瀏覽器中通常建議**停用**或忽略，因為它有時會導致更嚴重的漏洞。應優先使用強大的 **CSP** 取代此舊標頭。

# 開啟新分頁：Session Fixation/Theft & Information Leakage


> 小白的想法： 「這很簡單！既然我要開一個新頁面查餘額，而且新頁面需要知道『使用者帳號』跟『會員等級（VIP）』才能去資料庫撈資料，那我就用 URL 參數傳過去就好啦！
> 
> 
> 我把連結寫成：`https://bank.com/balance?user=wang_xiaoming&level=vip&account_id=12345`
> 
> 這樣新分頁一打開，後端程式碼只要讀取 URL 上面的 `user` 跟 `level`，就可以知道他是 VIP，然後顯示對應的餘額給他看。如果要再開下一頁，我就繼續把這些參數串在網址後面傳下去。」
> 
- **資安風險：**
    - **參數篡改 (Parameter Tampering) 與 IDOR：**
    這是最嚴重的風險。如果後端直接信任 URL 上的 `level=vip` 或 `user=wang_xiaoming`，駭客只需要把網址上的 `user` 改成別人的帳號，或是把 `level` 改成 `admin`，就能直接看到別人的餘額或取得管理員權限。這被稱為 **IDOR (不安全的物件直接參照)**。
    - **敏感資訊長期留存：**
    瀏覽器的歷史紀錄（History）、公司的 Proxy Server紀錄、以及網路服務供應商（ISP）的紀錄，都會完整保存 URL。這意味著即便使用者登出了，「使用者帳號」、「帳戶 ID」這些隱私資訊依然永久留存在各種 log 檔案中，隨時可能被有心人士翻出來。
    - **Referer 洩漏：**
    如果使用者在「帳戶餘額頁」點擊了一個外部連結（例如「聯絡我們」跳轉到外部客服系統），瀏覽器會自動送出 `Referer Header`，把包含你所有參數的完整網址傳送給那個外部網站。
- **防禦策略：**
    - **依靠 Cookie 或 LocalStorage 共享狀態，而非 URL：**
    瀏覽器設計上，**Cookie 是跨分頁共享的**（只要在同一個網域下）。
        - **正確做法：** 登入成功後，伺服器給瀏覽器一個加密的 `Session ID` (存於 Cookie)。
        - **新分頁行為：** 當使用者打開新分頁時，瀏覽器會自動帶上這個 Cookie。後端收到請求後，拿著這個 `Session ID` 去後端資料庫（Redis 或 SQL）反查：「這個 ID 對應的是誰？等級是什麼？」，完全不需要在 URL 上傳遞任何個資。
    - **後端驗證原則 (Trust No One)：**
    永遠不要相信前端傳來的「權限參數」（如 `level=vip`）。前端只能傳遞「我想看哪個帳戶的餘額（ID）」，後端必須自行檢查「目前登入的這個人，是否有權限查看該帳戶」。
    - **敏感參數放在 Body 透過 POST 傳輸（若非開新頁）：**
    雖然開啟新分頁通常是 GET 請求，但若是頁面內的查詢操作，應盡量使用 POST 方法，將參數放在 Request Body 中，避免顯示在網址列。

# 總結具體實作流程


1. **登入時 (Login):**
    - 使用者輸入帳密。
    - 後端驗證成功後，在伺服器建立一個 Session 記錄，儲存 `{ "user_id": 12345, "level": "vip" }` 等資訊。
    - 後端產生一個**隨機且安全的 Session ID**（例如 `XYZ`），並將它設定為一個 **`HttpOnly` Cookie** 發送給瀏覽器。

---

1. **開啟新頁面 (New Page Request):**
    - 使用者點擊「查看餘額」的連結：`https://bank.com/balance` (網址乾淨，不含參數)。
    - 瀏覽器**自動**將 `sessionId=XYZ` 這個 `HttpOnly` Cookie 帶入請求。

---


1. **後端處理 (Backend Processing):**
    - 後端伺服器接收到請求，從 HTTP 標頭中讀取到 `sessionId=XYZ`。
    - 後端根據 `XYZ` 去 Session 數據庫查詢，得到 `{ "user_id": 12345, "level": "vip" }`。
    - 後端程式碼知道使用者是誰，去資料庫撈取餘額，然後將餘額頁面的 **HTML 渲染後** 回傳給瀏覽器。
