### 1. 前端配置：`vite.config.js` 的作用與設置方法

**問題描述：**

前端使用 Vite 作為開發伺服器，`vite.config.js` 是配置的核心檔案，但可能存在以下問題：

- 硬編碼的 Port（5173）和代理目標（https://localhost:7221）缺乏靈活性，難以適應不同環境。
    
- 缺少環境變數支持，導致開發、測試和生產環境需要手動修改配置。
    

**原因：**

- Vite 配置未充分利用環境變數，導致硬編碼問題。
    
- 代理設置未與後端 Port 動態同步，可能導致 API 請求失敗。
    

**解決方案：**

- **明確 `vite.config.js` 的作用：** `vite.config.js` 用於配置前端開發伺服器的 Port、代理，以及其他構建選項。代理設置（`proxy`）用於將前端的 API 請求轉發到後端，解決跨域問題。
    
- **動態配置 Port 和代理：** 在項目根目錄創建 `.env` 文件，定義環境變數：
    
    ```
    VITE_PORT=5173
    VITE_API_PROXY=https://localhost:7221
    ```
    
- **在 `vite.config.js` 中讀取環境變數：**
    
    JavaScript
    
    ```
    import { defineConfig, loadEnv } from 'vite';
    
    export default defineConfig(({ mode }) => {
        const env = loadEnv(mode, process.cwd());
        return {
            server: {
                port: parseInt(env.VITE_PORT) || 5173,
                proxy: {
                    '^/api': {
                        target: env.VITE_API_PROXY || 'https://localhost:7221',
                        secure: false // 開發環境中忽略憑證驗證
                    }
                }
            }
        };
    });
    ```
    
- **支援多環境：** 為不同環境創建對應的 `.env` 文件，例如 `.env.development` 和 `.env.production`：
    
    Bash
    
    ```
    # .env.development
    VITE_PORT=5173
    VITE_API_PROXY=https://localhost:7221
    
    # .env.production
    VITE_PORT=5173
    VITE_API_PROXY=https://10.30.111.60:7221
    ```
    
    Vite 會根據 `mode` 自動載入對應的環境變數。

### 2. 前後端 Port 配置問題與協調策略

**問題描述：**

- 前端和後端的 Port 配置不一致，例如前端代理目標（`https://localhost:7221`）與後端實際運行 Port 不匹配，可能導致 API 請求失敗。
    
- 硬編碼的 Port 配置（如 `launchSettings.json` 中的 `https://localhost:7221`）在不同環境中需要手動調整。
    
- 環境變數未被充分利用，導致配置靈活性不足。
    

**原因：**

- 前端 `vite.config.js` 和後端 `launchSettings.json` 的 Port 配置未統一管理。
    
- 缺少環境變數支持，無法動態適應開發、測試和生產環境。
    

**Port 設定的優先級順序：**

理解 Port 設定的優先級非常重要，因為多個設定可能會產生衝突。

**前端 (Vite)：**

1. **命令列參數：** (`--port 3000`)
    
2. **環境變數：** (`VITE_PORT=3000`)
    
3. **`vite.config.js`：** 中的 `server.port`
    
4. **Vite 預設值：** (5173)
    

**後端 (ASP.NET)：**

1. **命令列參數：** (`--urls`)
    
2. **環境變數：** (`ASPNETCORE_URLS`)
    
3. **`Program.cs`：** 中的 `app.Run(url)`
    
4. **`launchSettings.json`：** 中的 `applicationUrl`
    
5. **`appsettings.json`：** 中的 `Kestrel` 設定
    
6. **ASP.NET 預設值**
    

**解決方案：**

- **後端 Port 設定：** 在 `Properties/launchSettings.json` 中定義後端 Port，並支持環境變數：
    
    JSON
    
    ```
    {
      "profiles": {
        "password_modifying_management.Server": {
          "applicationUrl": "https://localhost:7221;http://localhost:7221",
          "environmentVariables": {
            "ASPNETCORE_ENVIRONMENT": "Development"
          }
        }
      }
    }
    ```
    
    在 `appsettings.json` 中添加 `Kestrel` 配置作為備用：
    
    JSON
    
    ```
    {
      "Kestrel": {
        "EndPoints": {
          "Https": {
            "Url": "https://localhost:7221"
          }
        }
      }
    }
    ```
    
- **前端 Port 設定：** 在 `vite.config.js` 中使用環境變數動態設定 Port 和代理目標，並確保代理目標與後端 `applicationUrl` 一致。
    
    JavaScript
    
    ```
    // vite.config.js
    proxy: {
        '^/api': {
            target: env.VITE_API_PROXY || 'https://localhost:7221', // 對應後端 Port
            secure: false
        }
    }
    ```
    
- **同步前後端 Port：** 確保前端 `vite.config.js` 中的 `VITE_API_PROXY` 與後端 `launchSettings.json` 中的 `applicationUrl` 一致。在部署時，使用環境變數統一配置。
    
- **記錄實際使用的 Port：** 在 `Program.cs` 中記錄實際使用的 Port，便於調試：
    
    C#
    
    ```
    logger.Info("Application is listening on: {Urls}", string.Join(", ", builder.WebHost.GetSetting("urls")?.Split(';') ?? new[] { "未設定" }));
    ```

### 3. CORS 設置問題

**問題描述：**

- 在 `Program.cs` 中，CORS 配置使用了硬編碼的來源地址，缺乏靈活性。
    
- `var origins = builder.Configuration.GetSection("Cors:AllowedOrigins").Get<string[]>() ?? new[] { "http://10.30.111.60:5173", "https://10.30.111.60:5173" };`
    
- 硬編碼的 `http://10.30.111.60:5173` 在本地開發環境中可能導致 CORS 錯誤。
    
- 配置缺乏靈活性，無法適應不同環境的前端地址。
    

**原因：**

- CORS 配置未從 `appsettings.json` 完全動態載入，導致硬編碼問題。
    
- 未考慮本地開發環境（`localhost:5173`）和生產環境（`10.30.111.60:5173`）的差異。
    

**解決方案：**

- **將 CORS 配置移至 `appsettings.json`：** 在 `appsettings.json` 中定義允許的來源：
    
    JSON
    
    ```
    {
      "Cors": {
        "AllowedOrigins": [
          "https://localhost:5173",
          "http://localhost:5173",
          "https://10.30.111.60:5173",
          "http://10.30.111.60:5173"
        ]
      }
    }
    ```
    
- **動態載入 CORS 配置：** 在 `Program.cs` 中讀取配置並添加日誌：
    
    C#
    
    ```
    builder.Services.AddCors(options =>
    {
        var origins = builder.Configuration.GetSection("Cors:AllowedOrigins").Get<string[]>() ?? Array.Empty<string>();
        if (origins.Length == 0)
        {
            logger.Warn("No CORS origins configured. CORS will be disabled.");
        }
        options.AddPolicy("AllowReactApp", policy =>
        {
            policy.WithOrigins(origins)
                  .AllowAnyHeader()
                  .AllowAnyMethod()
                  .AllowCredentials();
        });
    });
    ```
    
- **支援環境變數：** 允許通過環境變數動態設定 CORS 來源：
    
    Bash
    
    ```
    export CORS_ALLOWED_ORIGINS=https://localhost:5173,http://localhost:5173,https://10.30.111.60:5173
    ```
    
    在程式碼中檢查環境變數：
    
    C#
    
    ```
    var envOrigins = Environment.GetEnvironmentVariable("CORS_ALLOWED_ORIGINS")?.Split(',') ?? Array.Empty<string>();
    var origins = envOrigins.Any() ? envOrigins : builder.Configuration.GetSection("Cors:AllowedOrigins").Get<string[]>() ?? Array.Empty<string>();
    ```

### 4. HTTPS 重定向問題：307 回應、Preflight 請求與網頁跳轉流程

**問題描述：**

在 `Program.cs` 中，HTTPS 重定向配置如下：

C#

```
app.UseWhen(context => !context.Request.Method.Equals("OPTIONS", StringComparison.OrdinalIgnoreCase), appBuilder =>
{
    appBuilder.UseHttpsRedirection();
});
```

目前的解決方案是在生產環境中註解掉 `HTTPS` 重定向，以避免問題。然而，這種方法有潛在風險，且未深入理解 HTTPS 重定向的原理、307 回應、Preflight 請求的原因，以及網頁跳轉流程。

#### 4.1 HTTPS 重定向與 307 回應的原理

- **HTTPS 重定向的運作方式：** ASP.NET Core 的 `UseHttpsRedirection` 中間件檢查進來的 HTTP 請求是否使用 HTTPS。如果請求是 HTTP（例如 `http://example.com:7221/api`），中間件會回應一個 **`307 Temporary Redirect`** 狀態碼，指示客戶端（瀏覽器或 API 客戶端）重定向到 HTTPS 地址（例如 `https://example.com:7221/api`）。
    
- **`307` 回應：** `307` 是一個**臨時重定向**，它會告訴客戶端使用**相同的 HTTP 方法**（例如 GET、POST）和請求主體，重新發送請求到新的 `HTTPS` URL。`307` 回應包含一個 `Location` 標頭，指定重定向的目標 URL。
    
- **網頁跳轉流程：**
    
    1. **客戶端發送初始請求：** 客戶端發送一個 HTTP 請求到後端（`http://example.com:7221/api`）。
        
    2. **伺服器檢查協定：** 後端的 `UseHttpsRedirection` 中間件檢測到請求是 HTTP，而非 HTTPS。
        
    3. **伺服器回應 307：** 伺服器返回 `307` 狀態碼，並在 `Location` 標頭中指定 HTTPS URL。
        
    4. **客戶端重定向：** 客戶端收到 `307` 回應後，自動發送新的請求到 HTTPS URL。
        
    5. **完成請求：** 伺服器處理 HTTPS 請求並返回最終回應。
        

#### 4.2 為什麼會有 Preflight 請求？

- **Preflight 請求的背景：** 當前端發送**跨域請求**時，若請求涉及**非簡單的 HTTP 方法**（例如 POST、PUT）或自訂標頭，瀏覽器會先發送一個 `OPTIONS` 方法的 Preflight 請求，以檢查伺服器是否允許該跨域請求（這是 CORS 機制的一部分）。
    
- **與 HTTPS 重定向的交互：** 如果 Preflight 請求使用 HTTP 發送，`UseHttpsRedirection` 中間件會試圖將其重定向到 HTTPS，這會導致一個 `307` 回應。然而，瀏覽器在處理 Preflight 請求時**不允許重定向**（基於 CORS 規範），因為重定向可能改變請求的上下文，導致 CORS 錯誤。
    
- **問題的根源：** 在開發環境中，前端可能使用 HTTP（例如 `http://localhost:5173`）發送請求到 HTTP 後端，但後端的 HTTPS 重定向會導致 Preflight 請求失敗。
    

#### 4.3 註解掉 HTTPS 重定向的風險

目前的解決方案是在生產環境中註解掉 `appBuilder.UseHttpsRedirection();`，以完全禁用 HTTPS 重定向。

**風險分析：**

- **安全性風險：** 數據以明文傳輸，可能被攔截或篡改，特別是在公開網路中。攻擊者可能執行中間人攻擊（MITM），竊取敏感數據（如 JWT 令牌、用戶憑證）。
    
- **不遵守最佳實踐：** 現代 Web 應用程式應強制使用 HTTPS，以確保數據完整性和機密性。
    
- **合規性問題：** 許多行業標準（如 PCI DSS、GDPR）要求使用 HTTPS 傳輸敏感數據。禁用重定向可能導致合規性違規。
    
- **瀏覽器警告與 SEO 影響：** 現代瀏覽器會對 HTTP 網站顯示「不安全」警告，影響用戶信任。搜尋引擎（如 Google）優先考慮 HTTPS 網站，禁用 HTTPS 可能降低網站的搜尋排名。
    
- **HSTS 無效：** 禁用重定向也會使 HSTS（HTTP Strict Transport Security）無效，客戶端將無法收到強制 HTTPS 的指令，可能繼續使用不安全的 HTTP 連線。
    

#### 4.4 建議的解決方案

- **在開發環境中允許 HTTP，生產環境強制 HTTPS：** 修改 `Program.cs` 根據環境動態啟用 HTTPS 重定向。
    
    C#
    
    ```
    if (app.Environment.IsDevelopment())
    {
        logger.Debug("Development environment: HTTPS redirection skipped to allow HTTP for local testing.");
    }
    else
    {
        app.UseHttpsRedirection();
        app.UseHsts();
        logger.Info("Production environment: HTTPS redirection and HSTS enabled.");
    }
    ```
    
- **在開發環境中使用自簽憑證：** 透過 `dotnet dev-certs https --trust` 生成自簽憑證，並在 `launchSettings.json` 中配置，讓開發環境也能在 HTTPS 下運行。
    
- **配置 HSTS 以增強安全性：** 在 `appsettings.json` 中定義 HSTS 參數，並在 `Program.cs` 中應用，確保客戶端在未來只使用 HTTPS 連線。

### 5. IIS 寫日誌權限問題

**問題描述：**

在 `Program.cs` 中，`EnsureLogDirectoryExists` 方法嘗試創建日誌目錄，但未充分考慮 IIS 部署時的權限問題。

**原因：**

- IIS 的預設權限未授予應用程式池寫入磁碟的權限。
    
- 錯誤處理不夠嚴謹，無法有效通知開發者。
    

**解決方案：**

- **增強錯誤處理：** 修改 `EnsureLogDirectoryExists` 方法，確保錯誤被記錄到 NLog，並拋出異常以防止應用程式在無日誌的情況下繼續運行。
    
    C#
    
    ```
    private static void EnsureLogDirectoryExists(ILogger logger)
    {
        try
        {
            // ... 創建目錄的邏輯
            logger.Debug("Log directory created successfully: {LogDirectory}", logDirectory);
        }
        catch (Exception ex)
        {
            logger.Error(ex, "Failed to create log directory: {LogDirectory}", Path.Combine(Directory.GetCurrentDirectory(), "Logs"));
            throw; // 拋出異常，確保應用程式不會在無日誌的情況下繼續運行
        }
    }
    ```
    
- **配置 IIS 權限：** 為 `Logs` 目錄授予應用程式池的寫入權限。在 Windows 檔案總管中，為 IIS AppPool\YourAppPoolName 使用者授予「修改」權限。
    
- **使用環境變數指定日誌路徑：** 在 `appsettings.json` 或環境變數中定義日誌路徑，提高配置的靈活性。
    

**遵循原則：**

- **可維護性：** 通過 NLog 記錄錯誤，便於追蹤問題。
    
- **KISS：** 簡單的權限配置和錯誤處理邏輯。
    
- **SOLID (OCP)：** 支援環境變數，適應不同部署環境。

### 6. 憑證基礎知識與管理指南

**什麼是憑證？** 憑證（Certificate）是一種數位文件，用來證明網站或服務的身份，並確保資料在網際網路上的傳輸是安全的。它類似於現實世界的身份證或護照，告訴瀏覽器和用戶這個網站是可信的。憑證由一個稱為憑證頒發機構（Certificate Authority，簡稱 CA）的組織簽發，包含網站的身份資訊（如域名）、公鑰，以及有效期限。

**為什麼需要憑證？**

- **安全性**：憑證啟用 HTTPS 協議，加密網頁與伺服器之間的通信，防止駭客竊取敏感資料（如密碼或信用卡號）。
- **信任**：瀏覽器會檢查憑證，確保網站不是假冒的，減少網路釣魚風險。
- **法規要求**：許多法律和標準（如資料保護法規）要求使用安全的連線。

**憑證的基本組成**

- **公鑰和私鑰**：公鑰用於加密資料，私鑰用於解密。公鑰包含在憑證中，私鑰必須保密並保存在伺服器上。
- **域名**：憑證指定了它適用的網域名稱（例如 example.com），只有匹配的域名才能使用該憑證。
- **有效期限**：每個憑證有開始和結束日期，過期後將無法使用。
- **簽名**：CA 對憑證進行數位簽名，證明其真實性。

**憑證會到期嗎？** 是的，憑證有固定的有效期（通常為 1 年或更長），這是為了確保安全性並遵循最新標準。過期後，網站將無法使用 HTTPS，瀏覽器會顯示警告，影響用戶體驗和網站可信度。以下是處理到期的方法：

- **檢查到期日期**：您可以透過工具查看憑證的詳細資訊。使用以下命令：
    
    text
    
    ```
    openssl x509 -in 您的憑證檔案.crt -text -noout | grep -A 1 "Validity"
    ```
    
    這會顯示「Not Before」（生效日期）和「Not After」（到期日期）。例如：
    
    text
    
    ```
    Validity
        Not Before: Oct  1 10:00:00 2025 GMT
        Not After : Oct  1 10:00:00 2026 GMT
    ```
    
    今天是 2025 年 10 月 23 日上午 11:55 (CST)，您可以根據這個日期計算剩餘時間。
- **提前更新**：在到期前 1-2 個月，向 CA 申請新的憑證。保留舊的私鑰（如果安全）可以簡化更新過程。
- **自動提醒**：使用監控工具或腳本定期檢查憑證狀態，及時通知您更新。

**如何獲取憑證？**

- **向 CA 申請**：聯繫一個可信的憑證頒發機構（如 Let's Encrypt、DigiCert 或其他商業 CA），提供您的域名資訊。
- **生成請求**：使用工具（如 OpenSSL）創建一個憑證簽署請求 (CSR)：
    
    text
    
    ```
    openssl req -new -newkey rsa:2048 -nodes -keyout 您的私鑰.key -out 您的CSR.csr
    ```
    
    輸入域名等資訊後，提交 CSR 給 CA。
- **接收憑證**：CA 會返回憑證檔案（通常是 .crt 格式），可能包含中繼憑證或根憑證。

**如何使用憑證？**

- **轉換格式**：伺服器軟體（如 Tomcat、Apache 或 IIS）可能需要特定格式（如 .pfx 或 .jks）。使用 OpenSSL 合併私鑰和憑證：
    
    text
    
    ```
    openssl pkcs12 -export -in 您的憑證.crt -inkey 您的私鑰.key -out 您的憑證.pfx -passout pass:您的密碼
    ```
    
- **配置伺服器**：將憑證檔案上傳到伺服器，並根據軟體說明（例如 Tomcat 的 server.xml）設定路徑和密碼。
- **測試連線**：使用瀏覽器訪問網站，確認鎖狀圖標出現，並檢查憑證詳情以驗證有效性。

**常見問題與解決方案**

- **域名不匹配**：如果憑證的域名與網站域名不同，需申請新的憑證。檢查憑證內容確保一致。
- **自簽憑證**：若暫時無法獲取 CA 憑證，可生成自簽憑證（openssl req -x509 ...），但需在本地信任該憑證以避免警告。
- **遺失私鑰**：私鑰遺失後，無法使用舊憑證，必須重新申請並生成新對。

**管理建議**

- **備份**：定期備份憑證和私鑰，儲存在安全位置。
- **更新計劃**：建立日曆提醒，確保在到期前更新憑證。
- **安全性**：保護私鑰免受未授權訪問，設置強密碼並限制存取權限。
